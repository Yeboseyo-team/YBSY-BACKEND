기준 문서: 「학기예보 요구사항 명세서」 (2026-10-13). 테이블은 명세서 5장, 예보 값은 4장 산출 규칙을 따릅니다.

## 파일 위치 (레포에 그대로 복사)

| 파일 | 용도 | 담당 |
|---|---|---|
| `supabase/migrations/20261013000000_init_schema.sql` | 테이블 4개 + RLS(5.5) + 가입 시 profiles 자동 생성 | 백엔드 |
| `supabase/seed.sql` | 자격증 15회차(실제 공고) + 데모 계정 (`supabase db reset` 시 자동 실행) | 백엔드 |
| `src/mocks/dummy-data.ts` | Supabase 없이 화면 개발용 목데이터, 타입, 예상 예보 결과 | 프론트 A·B |
| `scripts/generate-dummy.mjs` | **원본.** seed.sql과 dummy-data.ts를 같은 데이터로 생성 | 공용 |

데이터를 고칠 땐 `scripts/generate-dummy.mjs`만 수정하고 `node scripts/generate-dummy.mjs` 실행.
생성기는 명세서 4.5 검증 예시, 입력 범위(5장), 자격증 15~20종 등을 스스로 검사하고, 어긋나면 파일을 만들지 않습니다.

## 주의

- 자격증 날짜는 2026-10-14에 공고를 보고 넣은 값이에요. 화면에는 "최종 일정은 시행 기관에서 확인하세요"를 꼭 표시하세요(FR-04-5).
- 생성기는 4.5 검증 예시(김예보 8주차 57h)에 더해 **사전 검토 문구**와 **박운영 8주차 100% 경계값**도 스스로 검사해요. 데이터를 바꿔 이 장면이 깨지면 파일을 만들지 않아요.
- 운영 사이트도 같은 Supabase 프로젝트를 씁니다(팀 결정 10/14). 10/19에 팀원들이 테스트로 넣은 데이터를 정리하고 데모 계정 데이터를 생성기로 다시 넣습니다.
- **데모 계정 되돌리기:** `supabase/reset-demo.sql` 을 Supabase 대시보드 → SQL Editor 에 통째로 붙여 넣고 Run. 데모 계정 5명의 계획·자격증 선택·학기 설정·동의를 처음 상태로 되돌리고 공용 자격증 회차도 다시 맞춥니다. **실제 사용자(Google 로그인) 데이터는 건드리지 않아요.** 여러 번 실행해도 결과가 같아요. 생성기를 실행하면 이 파일도 같이 다시 만들어집니다. (2026-10-14 시험: 일부러 어지럽힌 데이터가 모두 복구되는 것 확인)
- Google로 처음 로그인하면 트리거가 profiles를 만들고 이름은 Google 프로필(`full_name`)을 씁니다.
- 학기 설정을 마친 데모 계정 4명은 개인정보 동의(`privacy_agreed_at`)도 된 상태입니다. DB에는 트리거가 동의 시각을 서버 시각으로 기록합니다.
- 접수 마감 회차 선택 불가(FR-04-2), 계획 30개 상한(FR-02-5)은 DB가 아니라 화면에서 막아야 합니다. DB에서 막으면 마감일이 지난 뒤 시드가 실패합니다.
- 확인: 실제 Postgres 16에서 migration + seed 2회 연속 실행 성공. 다른 사용자 계획 조회·수정 0건, 비로그인 자격증 조회 0건, 회원의 자격증·프로필 직접 추가 거부, 0.5시간 단위·학점·주차 순서·제목 30자 제약, Google 이름 반영까지 검증.
